# @hc1/design-system

Shared UI package for every HC1 IQ product — **ClinicalIQ**, **SourceIQ**, **HerCare**, and any future module. One source of truth for tokens, components, and the interactive playground.

Built on the [**shadcn/ui**](https://ui.shadcn.com) composition model — Radix UI primitives + Tailwind v4 utilities + `cva` variants — with HC1's design tokens baked in at the CSS layer. Consumers install a **compiled** package, not source.

- **Live playground:** https://pkhatrihc1.github.io/hc1-design-system/
- **Repo:** https://github.com/pkhatriHC1/hc1-design-system
- **Current version:** `0.10.0`

## Base library — why shadcn/ui

The design system's composition patterns come from **shadcn/ui**. That decision drives everything below.

**What we take from shadcn:**

- **`cva` + `cn` pattern** for variant + size + state. Every component uses `class-variance-authority` to declare variants and `clsx` + `tailwind-merge` to compose classes safely.
- **Radix UI primitives** for anything that touches focus management, keyboard, ARIA, portals, or overlays. We wrap Radix — we do not re-implement its behavior.
- **Tailwind v4 utilities** via `@theme` for utility class generation. Tokens are exposed as `--hc-*` custom properties, then re-declared inside `@theme` so classes like `bg-brand-500`, `rounded-control`, `text-body1` become available.
- **Semantic CSS var vocabulary** (`--primary`, `--card`, `--border`, `--ring`, etc.) so consumer code written the shadcn way — including code generated by the shadcn CLI in a consumer project — automatically inherits the HC1 palette.

**What we don't do:**

- **We do NOT use the shadcn CLI to copy components into this repo.** shadcn's CLI drops files into a consumer app; we wrap Radix primitives directly and layer HC1 tokens on top so every product sees the same tree.
- **We do NOT expose shadcn's default palette.** `shadcn-bridge.css` remaps every semantic var to an HC1 alias — the shadcn conventions stay, the visual identity is HC1.
- **We do NOT support dark mode yet.** HC1's semantic aliases have a single mode (light). Consumers keep their own `.dark { --primary: … }` overrides for now (see *Consumer setup* below).

**Why this matters for adopters:**

Products already using shadcn/ui (SourceIQ, ClinicalIQ, HerCare) migrate by swapping imports + renaming a small set of variants (`destructive → danger`, `default → primary`). No framework rewrite. See `docs/DESIGN_SYSTEM_MIGRATION.md` in the SourceIQ repo for a worked example.

## Distribution model

**Ships compiled**, not source. Every release includes:

| File | Purpose |
|---|---|
| `dist/index.js`   | ESM entry — components + tokens namespace |
| `dist/index.cjs`  | CJS entry |
| `dist/index.d.ts` | TypeScript types (ESM) |
| `dist/index.d.cts`| TypeScript types (CJS) |
| `dist/tokens/*`   | `./tokens` subpath — TS + types |
| `dist/playground.*`| `./playground` subpath — dev-only doc app |
| `dist/styles.css` | `./styles` subpath — HC1 tokens + shadcn bridge |
| `dist/tokens/css/*` | Source CSS files chained from `styles.css` |

**Why compiled**, not source-only (was source-only prior to 0.10.0):

- **No more type dedup gotchas.** Consumers used to type-check DS source, which meant DS's `@types/react` had to match consumer's exactly or TS threw "*Two different types with this name exist*". Compiled `.d.ts` files reference `react` and let the consumer's own `@types/react` resolve — this class of error is gone.
- **Faster consumer builds** — Vite/webpack don't re-parse DS's source tree per build.
- **Cleaner semver** — internal refactors that shuffle files don't leak into consumer type surfaces.

**How consumers install:**

- **Private Artifactory (target state):** `npm install @hc1/design-system@^0.10` with `.npmrc` pointing `@hc1:registry=https://hc1repo.jfrog.io/…`
- **Git URL (current):** `"@hc1/design-system": "github:pkhatriHC1/hc1-design-system#v0.10.0"` — the `prepare` script auto-runs `tsup` on install, so `dist/` always exists.
- **Local file: dep (monorepo dev):** `"@hc1/design-system": "file:../hc1-design-system"` — same auto-build via `prepare`.

## Consumer setup (must-do)

Two setup steps every consumer needs. Both are one-time.

### 1. Vite `resolve.dedupe` — REQUIRED

Without this, symlinked or `file:` dep setups end up with two React instances (DS's copy + consumer's copy) — runtime throws **"Invalid hook call"** the moment any DS hook fires.

```ts
// vite.config.ts
export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: {
    dedupe: ["react", "react-dom", "react/jsx-runtime"],
  },
});
```

Not Vite? Same principle applies — webpack `resolve.alias` or a monorepo `pnpm.overrides`.

### 2. `npm overrides` for `@types/react` — RECOMMENDED

Defense-in-depth. Even with compiled `dist/`, a transitive dep can pull in a different `@types/react` version and cause type conflicts.

```jsonc
// consumer's package.json
{
  "overrides": {
    "@types/react":     "$@types/react",
    "@types/react-dom": "$@types/react-dom"
  }
}
```

The `$@types/react` syntax forces every nested version to match the top-level one.

### 3. Import the styles once

```ts
// consumer's app entry (main.tsx, _app.tsx, etc.)
import "@hc1/design-system/styles";
```

This one import brings:
- HC1's primitive tokens (`--hc-color-brand-500` etc.)
- HC1's alias tokens (`--hc-color-action-primary` etc.)
- Tailwind v4 `@theme` mappings (so `bg-brand-500`, `rounded-control` are generated)
- shadcn semantic bridge (`--primary`, `--border`, `--ring`, `--destructive`, `--card`, `--popover`, etc.)

**If your app was using stock shadcn theme values**, remove them from your CSS — HC1's shadcn bridge takes over.

## Usage

```tsx
import { Button, Card, Dialog, Progress } from "@hc1/design-system";
import { primitives, aliases } from "@hc1/design-system/tokens";
import "@hc1/design-system/styles"; // once, at app entry

export function App() {
  return (
    <Card variant="elevated" density="comfortable">
      <Card.Header>
        <Card.Title>Vendor spend</Card.Title>
        <Card.Description>Last 30 days</Card.Description>
      </Card.Header>
      <Card.Content>
        <Progress value={72} tone="success" size="md" aria-label="Loading" />
      </Card.Content>
    </Card>
  );
}
```

To mount the interactive documentation app (dev-mode only, don't ship to production):

```tsx
import { DesignSystemPlayground } from "@hc1/design-system/playground";
```

### `@hc1/design-system/tokens`

Direct access to the three-layer token system:

- **`primitives`** — raw values (color scales, spacing, radius, typography). Never consumed by components directly.
- **`aliases`** — semantic roles (`color.bg.default`, `text.primary`, `spacing.stack.md`). The layer components consume.
- **`components`** — per-component token bundles (`button.paddingX`, `card.borderRadius`, etc.).
- **`types`** — shared TypeScript token types (`ColorScale`, `TypographyStyle`).

### `@hc1/design-system/styles`

The CSS bridge — every token exported as a `--hc-*` custom property, every shadcn semantic var (`--primary`, `--border`, etc.) mapped to an HC1 alias.

### `@hc1/design-system/playground`

The interactive documentation app. Dev-mode only — don't bundle into production.

## Architecture decisions

### 1. shadcn/ui composition, not shadcn CLI copies

We use shadcn's *patterns* (cva + cn + Tailwind + Radix) — not its CLI-copied component files. Every component in this DS is authored here, wrapping Radix primitives directly.

**Why:** CLI-copied components duplicate across products and drift. Centralizing the composition + tokens gives us a single upgrade path.

### 2. Radix primitives, always

For anything with focus/keyboard/ARIA behavior (Dialog, Popover, Tooltip, Tabs, Select, etc.) we wrap the corresponding `@radix-ui/react-*` package. We never reinvent focus traps, portal management, or roving-tab-index.

**Why:** Radix ships with correct accessibility semantics maintained by a dedicated team. We spend our time on visual + token layers.

### 3. Three-layer token system

`primitives` (raw values, never consumed) → `aliases` (semantic roles, what components read) → `components` (per-component bundles).

**Why:** Retinting the brand doesn't require touching component code. Every component reads aliases only, so a hex change in primitives cascades everywhere without a rewrite.

### 4. Ship compiled `dist/` (as of 0.10.0)

`tsup` outputs ESM + CJS + `.d.ts` + `.d.cts` + flat CSS. Prior versions shipped source-only.

**Why:** Type dedup — consumers used to type-check DS source, and any `@types/react` version drift produced *"Two different types with this name exist"*. Compiled `.d.ts` files reference `react` and defer to consumer's own types. Bonus: faster consumer builds, cleaner semver surface.

### 5. shadcn CSS-var bridge, not shadcn palette

`shadcn-bridge.css` maps `--primary`, `--card`, `--border`, `--ring`, `--destructive`, etc. onto HC1 alias tokens.

**Why:** Any code — including code generated by shadcn CLI in a consumer project — that reads `--primary` gets HC1's teal, not shadcn's slate. Keeps the shadcn ecosystem's conventions working while enforcing HC1 identity.

### 6. Compound components for structural primitives

`Card`, `Dialog`, `Drawer`, `Tabs`, `Alert`, `Popover`, `Tooltip`, `Breadcrumb`, `Radio` (as `RadioGroup`) use compound style: `<Card.Header>`, `<Dialog.Title>`, `<Tabs.List>`, `<Alert.Description>`.

**Why:** Enables context-based sub-behavior (auto-wired IDs for aria-labelledby, size inheritance) and reads more naturally than 8-way named exports (`CardHeader`, `CardTitle`, `CardDescription`, `CardContent`, `CardFooter`, `CardActions`, …).

**Trade-off:** shadcn's default pattern is named exports. Consumers migrating from stock shadcn rewrite their JSX (well-suited to a `jscodeshift` codemod).

### 7. `Select` uses options array, not compound children

```tsx
<Select
  value={statusFilter}
  onChange={setStatusFilter}
  options={[
    { value: "all", label: "All statuses" },
    { value: "active", label: "Active", group: "Live" },
  ]}
/>
```

**Why:** Serializable option lists, natural grouping via `group` field, keyboard/type-ahead handled once at the primitive level, no risk of stray non-`Option` children breaking behavior.

**Trade-off:** Consumers migrating from shadcn's `<SelectTrigger><SelectContent><SelectItem>` tree do a real refactor per Select. Simple flat cases are one-liners; grouped Selects with custom trigger rendering need care.

### 8. `lucide-react` as runtime dep, not peer

Icons are opinionated visual chrome. Consumers shouldn't pin a different `lucide-react` version and get unpredictable metrics.

### 9. Dark mode: not shipped yet

HC1's semantic aliases resolve to a single palette (light). Consumers who need dark keep their own `.dark { … }` overrides scoped to their app. When HC1 ships a dark ramp, the shadcn bridge will grow a `.dark { --primary: var(--hc-color-brand-…dark); }` block and consumers can delete their overrides.

### 10. Static playground preview via GitHub Pages

The playground (`src/DesignSystemPlayground.tsx` + `preview/`) auto-deploys to https://pkhatrihc1.github.io/hc1-design-system/ on every push to `main`. Design + engineering + PM review changes without needing a local checkout.

## Development workflow

```bash
# 1. Install
npm install                # runs tsup via `prepare` — dist/ ready

# 2. Iterate
# Option A: run a consumer app (SourceIQ, ClinicalIQ) locally — file: dep picks up edits
# Option B: run the playground locally
cd preview && npm install && npm run dev

# 3. Typecheck (fast — no emit)
npm run typecheck

# 4. Build (updates dist/, needed before pushing so consumers on git URL see changes)
npm run build

# 5. Playground auto-deploys to GH Pages on push to main
git push
```

**Adding a component:**

1. Create `src/components/<name>/{Name.tsx, Name.types.ts, index.ts}` — Radix wrapper + cva variants + `--hc-*` token consumption.
2. Add `export * from "./<name>";` in `src/components/index.ts`.
3. Add matching `src/docs/components/<Name>Doc.tsx` playground page.
4. Register in `src/docs/registry.ts` (id, label, category, Component).
5. Update this README's component table.
6. Update `CHANGELOG.md` with the addition.

## Versioning strategy

**Current release: `0.10.0` — pre-1.0.** The public API is stable-in-intent but has not yet survived a full product migration, so any `0.x.y` → `0.x.z` change may still break consumers. Pin exact versions during the migration window.

**1.0.0 will ship only when all four gates are cleared:**

1. ClinicalIQ is fully migrated onto `@hc1/design-system`.
2. SourceIQ is fully migrated onto `@hc1/design-system` (in progress — see `sourceiq-hc1com/docs/DESIGN_SYSTEM_MIGRATION.md`).
3. The legacy design systems inside both products are removed.
4. The public API has absorbed at least one round of migration feedback without a breaking change.

**Post-1.0 semver:**

- **Major** (`2.0.0`) — breaking change to any public export: removed component, renamed prop, moved subpath entry, removed token, or changed token value in a way that shifts pixel output.
- **Minor** (`1.1.0`) — new component, new prop (backward-compat), new token, new subpath entry.
- **Patch** (`1.0.1`) — bug fix, doc update, internal refactor with no public API change.

Token-value tweaks that visually shift output (a hex change, a radius jump) are treated as breaking — bump major.

## Contribution guidelines

1. Read `FOUNDATION.md` at the repo root before adding anything. It defines what the design system will and won't do.
2. Before adding a new component, check if it already exists — never fork.
3. Every component ships with: `<Name>.tsx`, `<Name>.types.ts`, `index.ts`, matching `<Name>Doc.tsx` in the playground, and a registry entry.
4. Every design decision must trace back to a token. No raw hex, no off-scale spacing.
5. New Radix primitives added → declare in `peerDependencies` (not just `devDependencies`) so consumers install them.
6. Update `CHANGELOG.md` in the same PR as the code change.
7. `npm run typecheck && npm run build` must be clean before pushing — the playground preview deploy will fail otherwise.
